## 建议详情

### OPT-001 · 主备读取错误处理

- 依据：[state-read.ts](../product/state-read.ts)、[http.test.ts](../product/tests/http.test.ts)。主线路慢于 4.5 秒启动备用线路；任一路线返回部分 4xx 时可立即结束读取。
- 建议：补测备用线路先返回 403/404/429、主线路随后成功的场景；明确区分真实认证失效与线路级错误，不忽略有效的 401，不自动重放用户写操作。
- 验收：线路级失败不会阻断另一条健康线路；总超时仍受限，退出登录仍能取消请求；正常主线路仅发一次请求。
- 成本：小至中；风险：认证处理、额外请求量。先用测试验证，暂不认定为线上故障。

- 状态更新（2026-11-27）：[修复提交 6afb7c6](https://github.com/rainy256/qidongapp/commit/6afb7c636ccad43ea6b564a2f98d1d4933cbac39) 已实现主备线路错误仲裁，仅明确的 Worker 401 unauthorized 立即终止；其他线路错误等待健康线路，保留统一截止时间与取消机制。新增测试覆盖备用线路先返回 403/404/429、主线路失败后启动备用、非明确 401、双线路失败、取消及 POST 不自动重放。[该提交基础检查 CI](https://github.com/rainy256/qidongapp/actions/runs/45939564805) 已成功。代码及自动化验收层面已完成；最新正式 Release 仍为 v0.1.7，未确认修复已进入正式 APK，也未重新执行真机测试。线路健康状态的实际测量仍归 OPT-002，不重复追加建议。

### OPT-002 · 先测耗时，再优化

**本轮处置（2026-11-27）**　在「我的 → 网络耗时诊断」手动开始一轮测量。每类最多保留最近 100 个样本；读取与保存分别统计成功次数、成功耗时 P50/P95、客户端超时比例，另列备用线路比例和断网恢复到新请求成功的耗时。退出账号清空记录。真机 Wi-Fi、移动网络和弱网基线留给候选版按[记录表](DEVICE_CHECK.md)分别填写。

- 依据：[refresh-loop.mjs](../product/refresh-loop.mjs)、[worker/index.mjs](../product/worker/index.mjs)、[confirmed-write.ts](../product/confirmed-write.ts)。已有退避、重连补刷、确认写入后更新界面和 D1 batch 优化。
- 建议：利用现有 Worker 日志和必要的匿名客户端诊断，测量读取、保存耗时分布（P50/P95）、超时率、备用线路启用率及网络恢复到成功同步的时间。
- 验收：分别记录 Wi-Fi、移动网络、弱网及重连场景，可重复比较优化前后效果；不采集令牌、口令或成员私密日程。
- 成本：中；风险：诊断开销和隐私。优先轻量方案。

### OPT-003 · 更友好的同步状态

**本轮处置（2026-11-27）**　首页小队卡片显示最近一次成功读取距今多久。有旧快照时，一次失败只显示重连状态，连续失败才显示醒目提示；首次同步失败单独说明。成功刷新后自动恢复。单项写入确认不会刷新整队同步时间。

- 依据：[main.tsx](../product/main.tsx)。已有独立同步错误提示、手动刷新及自动重试。
- 建议：在小队区域显示最后一次成功同步时间（刚刚更新/N 分钟前/正在重连），区分首次加载与旧快照暂未刷新；短暂失败使用低干扰提示，持续失败再突出显示。
- 验收：断网后仍可查看已有快照且明确其可能过期，恢复后提示自动消失；登录失效不会被弱化为普通网络错误，不伪造成功写入。
- 成本：小；风险：过期数据误读。

### OPT-004 · 下一段连续重合空闲

**本轮处置（2026-11-27）**　关闭。固定三人小队已有日程页的三人共同空闲、预约预填及车票改约入口；两人有空仍需单独确认第三人的时间。在已有入口不足以完成具体任务前，首页保留即时发车。

- 依据：[PRODUCT.md](PRODUCT.md) 及现有日程推荐逻辑。
- 建议：在首页突出下一段满足所选时长的三人连续重合时间，没有三人时可展示两人重合并进入现有预约流程。严格区分未填写与明确没空。2026-11-27 已核对 [HomeView.tsx](../product/components/HomeView.tsx)、[main.tsx](../product/main.tsx)、[features.tsx](../product/features.tsx) 与 [rebook.mjs](../product/rebook.mjs)：已有日程页共同空闲列表、预约预填入口和车票改约时的冲突过滤，但首页没有独立的下一段共同空闲入口，候选时长目前固定为两格（1 小时）。复用现有连续交集算法和预约冲突过滤，增加独立入口及可选时长；两人候选也必须保证同一成员组合连续覆盖所选时长。
- 验收：覆盖跨午夜、已过时段、时长不足、周滚动和时区边界；不自动修改成员日程或创建预约。
- 成本：小至中；风险：时间边界及重复推荐。复用现有算法。

### OPT-007 · 快捷填充时保护已有日程草稿

**本轮处置（2026-11-27）**　快捷操作将替换非空时段时先展示日期和目标范围，取消即保留原草稿。未保存的编辑随当前成员在内存中跨页面保留；七天窗口滚动按绝对日期保留交集，新增日期读取服务端日程。跨设备更新保留原 revision，整周没空在窗口扩展后需重新确认。组件测试覆盖替换、取消、切页、跨日和 revision。

- 依据（2026-11-27 静态审阅）：[ScheduleEditor.tsx](../product/components/ScheduleEditor.tsx) 的 applyQuickSpan 直接把当前日期的草稿数组替换成单一时段；「跟队友重合」「全天都有空／剩余时间都有空」均复用该函数。先手动编辑两段时间再点快捷填充时，原草稿会被替换。这是源码中可确认的行为，不代表服务器已保存的数据会自动丢失。
- 建议：空草稿直接填充，有内容且会被覆盖时显示简明的替换预览及一次撤销入口，或轻量确认。不要擅自合并不连续时段或将未选择的空闲时间标记为可用。撤销只恢复当前日期的原草稿及编辑状态，不修改其他日期、不发写请求。
- 验收：两段已有草稿 → 点快捷填充 → 撤销，应恢复原两段；相同结果不产生多余提示；切换日期、轮询更新、保存冲突不让撤销误作用于其他草稿或覆盖服务器新版本；显式不可用、过去时段保护及 revision 并发校验继续通过。新增组件交互测试，真机检查触控流程。
- 成本：小；风险：撤销与跨设备 revision 的一致性。先处理当前日期的单次撤销，不做复杂历史系统。
- 补充（2026-11-27 再次审阅）：[main.tsx L384–396](https://github.com/rainy256/qidongapp/blob/42cff00706686c13b338ca225bd8ce3d34e9470f/product/main.tsx#L384-L396) 的日程标识随七天窗口首日变化，且 [L652–704](https://github.com/rainy256/qidongapp/blob/42cff00706686c13b338ca225bd8ce3d34e9470f/product/main.tsx#L652-L704) 仅在日程页挂载编辑器；底部导航直接切换页面。[ScheduleEditor.tsx L120–155](https://github.com/rainy256/qidongapp/blob/42cff00706686c13b338ca225bd8ce3d34e9470f/product/components/ScheduleEditor.tsx#L120-L155) 的本地草稿会随组件卸载或窗口标识变化而丢弃。建议将未保存草稿及其基础 revision 提升至会话级内存，或在主动切页前提供保存/保留/放弃选择；跨北京时间 06:00 时仅将仍在新窗口内的绝对时段映射回草稿，提示已过期内容及版本冲突，不静默覆盖其他设备修改。验收增加：编辑两天后切到消息再返回、通知跳页、05:59 到 06:00 自动刷新、跨设备 revision 变更、退出登录切换成员；未确认的草稿不能串账号或被当成已保存数据。优先采用内存方案，不默认持久化私密日程。未真机复现；不代表服务器数据丢失。

### OPT-008 · 减少首页无意义的时钟刷新

**本轮处置（2026-11-27）**　首页使用单调时钟按同步分钟、半小时、车票到期、ETA、可喊截止和在线状态边界更新，进入后台后停止 UI 计时。固定空闲快照下用 React Profiler 和可控时钟比较 60 秒，原版计时更新 120 次，新版 1 次（均不含首次挂载和网络轮询）。这是渲染次数，不是设备耗电数据。

- 依据（2026-11-27 静态审阅）：[HomeView.tsx](../product/components/HomeView.tsx) 挂载时每 500ms 更新 tick，使首页函数重新执行，重新计算邀请状态、成员可喊状态、备选预约并生成车票列表；visibilitychange 只更新时间，没有显式停止该定时器。定时器名义上每分钟触发 120 次，不等于已测得 120 次实际提交渲染，也不能据此断定耗电或卡顿。
- 建议：先在同一设备的测试构建中利用 React DevTools/Profiler 记录渲染次数和 actualDuration；若确有冗余，将时钟状态缩小到受影响组件，或根据文案分钟边界及最近的车票过期、可喊截止、ETA、在线状态 90 秒边界调度下一次更新。利用已有可见性及 Capacitor App 生命周期，后台暂停 UI 时钟，回到前台立即重算。保留服务器快照与单调时钟的时间推算，不改变网络轮询策略，不默认引入复杂缓存。
- 验收：同快照、同设备对比一分钟首页空闲场景的提交次数与渲染耗时；以无变化时至少减少一半提交次数作为待测目标。测试过期、可喊、ETA、重连和前后台切换的临界时刻，前台状态仍及时准确，后台不主动维持 UI 定时器，不增发请求。
- 成本：小至中；风险：降低刷新频率导致到期状态滞后；用边界测试及实际测量决定方案。当前无性能实测结果。
- 外部参考（2026-11-27 查阅）：[React Profiler](https://react.dev/reference/react/Profiler)、[MDN Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)。用于性能测量及页面可见性管理，非特定华为 WebView 的实测结论。

### OPT-009 · 预约表单不应静默更换已选择的开始时间

**本轮处置（2026-11-27）**　显式选择的开始时间失效时保留原值，提示重新选择并禁用提交。用户可以一键选择能容纳原时长且不与现有预约冲突的下一时段。新建及改期共用此逻辑，半小时边界和服务器快照均可推进校验。

- 类别：时间与日程；优先级：P1；状态：建议实施（静态审阅确认分支行为，未真机复现）。
- 依据：[features.tsx L349–392](https://github.com/rainy256/qidongapp/blob/42cff00706686c13b338ca225bd8ce3d34e9470f/product/features.tsx#L349-L392) 中 ReservationPanel 的 effectiveFrom 在已选 from 不再处于未来七天有效范围时回落到下一可用时间；valid 和 submit 均使用回落后的值。后台刷新 now 跨半小时边界时，用户已明确选择的时间可能在未操作表单的情况下变化。改期流程也共用此逻辑。现有 [logic.test.mjs](../product/tests/logic.test.mjs)、[worker.integration.test.mjs](../product/tests/worker.integration.test.mjs) 检查时段边界及预约服务端逻辑，但此次查看未见针对这一表单交互的回归测试。
- 建议：区分「尚未选择，自动初始化」和「用户已明确选择，但时间已失效」。前者允许随当前时间推荐；后者保留原选择并提示“所选时间已过，请重新选择”，禁用提交，提供一键选下一可用时段；只有用户主动确认才更新 from。不要改变原有预约时长、游戏、冲突检测、revision 和服务端校验，不新增 API。
- 验收：例如 20:29 选择 20:30 开始，轮询进入 20:30 后，不得未经重新选择直接提交 21:00。分别覆盖新建/改期、北京时间 06:00 窗口滚动、末日越界、预约冲突、正常刷新不影响有效选择，以及自动初始化无障碍提示。使用可控时钟和组件交互测试，真机验证。无请求成功前不显示已预约。
- 成本：小；风险：旧选择过期时增加一次操作，但可避免错误时间通知全队。当前未发现实际误预约记录，也未执行线上写入测试。
