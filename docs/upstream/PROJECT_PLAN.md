# 项目总规划书（Project Plan）

本文档沉淀了从需求讨论（Antigravity × Codex `gpt-6.2-astra / xhigh` 两轮深度收敛）到多轮手机端审美迭代后最终敲定的产品、算法、视觉与工程全案。

---

## 1. 产品定位与核心解决的痛点

- **目标场景**：国内微信群 / QQ 群熟人开黑约局（`Apex`、`GTA`、`塔科夫`、自定义组局），解决 When2meet 在手机端难涂格子、群接龙难统计重合时间、跨零点时间混乱的问题。
- **使用原则**：
  1. **零登录进房**：群友点开 `/r/{id}` 直接看当前进度与填写，**首次点击保存时才创建数据库参与者记录**，避免微信聊天预览/路过打开产生僵尸空位。
  2. **彻底取消 `?admin=` 管理链接**：地址栏永远只有一个干净的群邀请链接 `/r/{id}`，防止房主误把带管理密钥的地址发到群里。房主凭证与成员编辑凭证全部通过 `HttpOnly; Secure; SameSite=Lax` Cookie 下发，同源写接口校验 `Origin`。
  3. **三态明确区分**：系统严格区分「未提交」「有空时段」「明确这次都不行」，绝不对未填者点名催促，只客观统计已提交名单，且提供一键「这次都不行」避免群里反复追问。
  4. **草稿反馈与正式结果分离**：顶部车票只展示「已提交快照」算出的正式推荐；底部悬浮反馈气泡展示「其他人最新提交 + 我当前未保存草稿」试算的结果，清晰标注 `尚未保存`。

## 2. 视觉风格与手机端交互定稿（用户已拍板）

> **⚠️ 视觉铁律（不可退回修改）：**
> 1. **主攻手机端（微信/QQ 内置浏览器单手大拇指体验）**：全站以 `max-width: 460px` 居中舞台展示（手机全宽贴合安全区），不采用臃肿的桌面双栏表格布局。
> 2. **全站严禁使用绿色**：用户明确不喜欢绿色。主色采用 **奶油蓝莓紫（`#4E5CD6`）** 表示「可开/主按钮」，**珊瑚蜜桃粉（`#FF7D6B`）** 表示用户自己的时段与手账点缀，**奶酪鹅黄（`#FFF6D4` / `#854B00`）** 仅用于「还差 1 人」提醒，背景为 **暖奶白点阵手账底（`#FFFBF4`）**。
> 3. **小黄豆主题美术素材**：顶部与游戏预设卡已确定采用用户上传与风格对齐的「3D 圆滚滚小黄豆」系列图（位于 `public/art/`）。

### 已锁定的核心页面交互

- **建房页 `/` (`CreateRoomPage`)**：
  - 顶部横排卡片：左侧完整竖版狂奔小黄豆（`hero-runner.png`），右侧「飞奔赶来开黑中 · 今晚约谁一起玩？」。
  - 2×2 游戏贴纸墙：`Apex`（默认 3 人）、`GTA`（默认 4 人）、`塔科夫`（默认 4 人）、`自定义`（点击后清空标题并自动聚焦输入框）。
  - 撕页迷你日历（周末自动蜜桃色顶条，工作日素色，选中弹起）+ 晚间起止 `<select>` + 几人发车步进器（联动彩色席位圆点预览）+ 最短游玩时长胶囊。
  - 纯实底吸底主按钮 `生成开黑车票`。
- **房间车票页 `/r/:id` (`RoomPage`)**：
  - **开黑发车票 (`RecommendationCard`)**：展示对应游戏小黄豆贴纸、撕票锯齿腰线、大号「`周五 20:00 开`」、可点击跳转的席位头像行（`[阿哲] [老周] [七七] [小满] [+ 等你上车]`）、一键复制群通知（Clipboard API 失败时自动回退同步 `execCommand` 或原地展开只读 `<textarea>` 供长按复制）。
  - **单手选时区 (`NightEditor`)**：夜晚标签直接标出每晚峰值空闲人数（`周五 27 · 4人空`）；提供 **`⚡ 跟大家一起 XX:XX–XX:XX`** 与 **`🌙 整晚都有空`** 一键预填；底层采用微信 WebView 最稳定的原生 `<select>` 起止卡片（显式标注 `次日 00:00`），支持「加第二段」保留中间吃饭空档。
  - **波浪分布条 (`DensityBar`)**：上轨为按人数变化的蓝莓紫波浪柱（扣除自己旧记录），下轨为珊瑚粉「我的上车时段」胶囊；手机点击小格不误触发，另设 `44px` 合规触区的「查看人数」展开合并时段名单。
  - **吸底悬浮栏 + 延迟昵称弹窗 (`NicknameDialog`)**：取消常驻昵称框，把实时试算气泡与「保存我的时间 / 这次都不行」固定在纯实底吸底栏；首次保存无昵称时才弹出原生 `<dialog>` 底部抽屉「上车报个名～」（支持中文输入法防误提交 `isComposing || keyCode === 229`）。

## 3. 核心算法：全程连续人员交集推荐引擎

详见 [`src/domain/recommend.ts`](../src/domain/recommend.ts)（已配 5 项单测，可前后端复用）：

1. **左闭右开半小时整数格点 `Slot`**：`Slot = Math.floor(utcMs / 1_800_000)`，界面按 `Asia/Shanghai` (+08:00) 渲染；跨零点自然递增，绝不产生负时长。
2. **先合并、再求全程交集**：
   - 先按人、按晚归并重叠或首尾相接区间（`[19:00, 20:00)` + `[20:00, 21:00)` → `[19:00, 21:00)`），同时严格保留 >= 1 格的吃饭空档。
   - 枚举每一个合法开局格 `s`，只收录在 `[s, s + durationSlots)` **全区间连续有空** 的成员集合 `G`。
   - 对同一非空 `G`，计算覆盖 `[s, s + durationSlots)` 的连续交集边界 `[L, R)`，生成 `firstStart = max(L, earliestStart)`、`lastStart = R - durationSlots`、`availableUntil = R`，并按 `(nightId, memberIds, firstStart, R)` 去重合并，避免同一晚霸屏 Top 3。
   - **中途有人加入不会截短原阵容原本可玩的更长连续窗口**。
3. **排序规则**：
   - `missingPlayers === 0`（达到门槛）优先 → `missingPlayers` 更少 → `firstStart` 更早 → 连续可玩总时长 `(availableUntil - firstStart)` 更长 → 实际人数更多 → `nightId` / 稳定 ID 兜底。
4. **必测防误报反例（已在 `recommend.test.ts` 验证）**：
   - 条件：要求 4 人连玩 2 小时（4 slots），甲乙丙 `20:00–22:00`，丁 `20:00–21:00`，戊 `21:00–22:00`。
   - 虽然每个半小时格都是 4 人有空，但推荐引擎必须准确输出 **`[甲, 乙, 丙]` 还差 1 人**，绝不误报 4 人可开；当最短时长改为 1 小时（2 slots）时，准确拆出 `20:00 [甲乙丙丁]` 与 `21:00 [甲乙丙戊]` 两个 4 人可开窗口。

## 4. Phase 2 后端与部署架构（历史方案 A，现作为备用）

- **技术栈**：`React + Vite + TypeScript`（已完成） + `Fastify (Node.js + TS)` + `SQLite (better-sqlite3, WAL 模式)` + `SSE (Server-Sent Events)` + `Nginx` + `systemd` 单进程托管。
- **双版本号并发控制**：
  - `roomRevision`：房间全局版本号（任意成员保存或房主关房事务提交后递增），仅用于 SSE 推送版本通知与客户端去重防倒序。
  - `mineRevision`：单成员个人版本号（首次为 `0`），写接口只比对本人的 `baseMineRevision === participant_rev`，两个朋友同时保存互不产生 409 冲突；同时通过 `mutationId` 做幂等重试保护，弱网超时重发不重复报错。
- **实时同步策略**：
  - `GET /api/rooms/:id/events` 建立 SSE 长连接，仅推轻量 `{ roomRevision }`，客户端确认高于本地版本后请求 `GET /api/rooms/:id` 拉取权威快照（收到推送时保留未提交的本地草稿）。
  - 监听 `visibilitychange`：切后台/微信退出页面时断开或暂停，切回前台立刻校准最新 `roomRevision` 并重连；SSE 不可用时前端自动降级为 6 秒可见态轮询。
  - **Nginx 必配避坑**：事件流路由必须设置 `proxy_buffering off;`、`proxy_cache off;`、`gzip off;`，`proxy_read_timeout` 长于服务端 SSE 心跳间隔（如心跳 25s、超时 90s）。

## 5. 功能分期与真机验收清单

### MVP 阶段（前后端已实现，实际部署和验收待完成）
- 选具体几晚 + K 人门槛 + 最短时长建房
- 普通群链接直达 `/r/:id`、Cookie 识别身份、Origin 校验
- 按晚直选起止时间（含跨零点 `次日` 标注）、一键快捷时段、加第二段、这次都不行
- 蓝莓紫波浪分布条 + 实时凑齐气泡 + 全程交集推荐车票 + 群通知一键复制（含微信剪贴板降级）
- SSE 实时同步（带切前台校准）与房主结束收集（原生 `<dialog>` 二次确认）

### V1.1 后续增强（MVP 稳定后再做）
1. 房主「就定这场」定场锁定（锁定后如有成员改时间掉出，不默默改推别的时段，而是明确提示 `原定场次现有 3/4 人`）
2. 三态意愿「可凑（待定）」及「问问某某确认即可成局」提示
3. 个人一次性高熵换机恢复链接、`.ics` 日历导出、房主移除捣乱记录

### 坚决砍掉的伪需求
- 每周固定习惯模式（跨夏令时与自然周截断复杂）、账号注册登录体系、4 位数字认领码（易枚举）、移动端自由拖拽涂格子、实时输入光标、内置聊天室与机器人。

### 上线前必跑 3 个真机验收用例
1. 两台手机（微信内置浏览器）同时点保存不同人的时段，均成功且互不报 409 冲突；
2. 微信内切回聊天窗口后再切回页面，无需手动刷新即可自动同步他人的最新提交；
3. 在真实后端复跑 `甲乙丙 20–22 / 丁 20–21 / 戊 21–22` 反例数据，确认不会误报为 4 人可连玩 2 小时。


## 当前部署决策：Cloudflare Workers + D1

无需自购服务器。静态资源与 API 同源；Cloudflare 版以 6 秒可见态轮询代替 SSE，切回前台立即校准。匿名 Cookie 先建立会话，HMAC 派生房间/身份，D1 SQL 触发器原子提交变更。原 Fastify + WAL + SSE 保留，数据库不共享。以 [CLOUDFLARE.md](CLOUDFLARE.md) 为部署指南。代码完成不代表真实账户部署及微信实测通过。
